# Agent Note: 开发管理交付闭环

Status: implemented

[English](2026-09-07-development-management-delivery-loop.md) | 中文

## Problem

Buddy 已有专业会话身份和资料库，但缺少从产品需求到各专业工程师的持久化交接，也缺少从已上传研发成果到合并决策的证据链。只有可视化任务看板会造成“已经协作”的假象，却不能约束谁可以执行操作。固定返回“Agent 审查通过”更危险：系统可能在未读取 Git 状态、未执行检查、未获得人工和远程系统证据时声称分支安全。

## Decision

Buddy 提供独立的开发管理 Host 服务和浏览器工作区。产品经理可创建、提交、指派、备注和查看需求；区块链架构工程师、算法工程师和智能体应用开发工程师只能查看并修改与其专业匹配且已指派给自己的任务。Host 负责角色鉴权，并维护从草稿、指派、开发、成果验收、交付审查、人工确认、已提交 Merge Request 到已合并的封闭状态生命周期。

工程师至少上传一个成果文件并填写成果说明后，才能提交验收。产品经理查看成果后，可填写可选意见并通过，或填写必填原因后退回。被退回的任务重新开放研发上传和再次提交。首次 Agent 交付检查只对验收通过的成果开放；Agent 暂缓的任务仍可重试检查。成果说明、审核决定和意见作为任务正式数据与不可变审计事件持久化，Host 独立于浏览器 UI 强制执行全部角色和状态门槛。

需求和原型文档使用明确的产品经理格式白名单。研发上传代表完整仓库，因此在通过角色、状态、路径、重复路径、单文件和单任务校验后，允许任意普通工程文件。HTTP 请求体流式写入私有临时文件，计算 SHA-256，并在原子提交时再次校验；大型模型权重不会整体成为内存值。

只有在本地仓库规范路径被证明位于配置根目录内后，交付审查才会读取该仓库。Git 命令使用参数数组。Agent 记录当前分支和工作区状态，比较 `target...source`，计算行数，寻找共同基线后双侧都修改的文件，并参考 `merge-tree` 冲突信号。配置的检查、测试与构建命令通过受管子进程服务执行，具有时间和输出限制。持久化报告包含全部证据、确定性 MR 文本，以及“建议合并”或“暂缓合并”；存在冲突、失败检查或没有提交差异时不能建议合并。

建议合并只能进入 `awaiting-human-confirmation`。产品经理必须显式确认生成的 MR 内容。配置 GitLab 后可真正创建并在后续合并 MR；未配置时，Host 要求提交阶段提供有效的人工 MR URL，完成阶段提供有效的已合并 URL。系统不声称已实现 GitHub 自动创建，也不会伪造分支审查、MR 提交或合并状态。

## Alternatives considered

**把流程实现为聊天提示词和现有资料库文件。** 未采用，因为聊天没有封闭任务生命周期、指派人鉴权、原子审计记录或机器强制的人工确认门槛。

**研发工程文件只允许预先整理的扩展名。** 未采用，因为完整 Solidity、Python、前端和 Java 仓库包含资源、Wrapper、Native 文件、模型 Sidecar 和无扩展名配置；白名单会让“上传完整工程”在不报错的情况下变成假需求。

**未配置远程提供方时返回模拟成功 MR。** 未采用，因为这会错误描述外部状态。人工 URL 证据保证隔离网络演示真实可信，GitLab 配置则提供真正自动化。

**Agent 检查干净后立即提交。** 未采用，因为产品要求保留人工决定权；即使所有自动检查通过，进入“已提交合并请求”仍必须由产品经理操作。

## Consequences

本功能在隔离客户网络内仍可使用，同时提供可审计的端到端协作路径和真实本地交付证据。代价是新增私有持久化存储、潜在大型附件、长时间受管检查和部署方维护的仓库根目录。疑似冲突仍是保守信号，不等同于确认的合并冲突。GitHub 自动创建 PR、逐命令实时日志、附件替换和保留策略仍属延期能力，并以明确限制呈现，而不是暗示已经支持。
